# Планирование реализации

Прочитать AGENTS.md, backlog/AGENTS.md и docs/requirements/README.md.
Планирование не разрешает изменение приложения. Уважать уже данный запрос
на реализацию: не просить повторного разрешения.

## Готовность

Проверить source task, дубликаты, зависимости и требования. Все REQ готового
плана должны быть приняты. Для изменения поведения обновить целевой текст REQ
до реализации и сбросить реализованность новой редакции. `none` допустим лишь
с конкретной причиной сохранения поведения. `pending` не допускается в готовом
плане; черновик имеет readiness: no и задачу в needs-clarification.

Закрыть продуктовые и существенные технические решения с источником решения.
Игровые механики сверить с правилами; UI описать с состояниями и критериями
приёмки; изменение сохранённых данных — с совместимостью и восстановлением.
Для существенного архитектурного выбора использовать architecture-decision.
Обычные локальные детали в рамках контрактов оставить исполнителю.
Если решение отсутствует, записать конкретный вопрос и продолжить независимые планы.

## Компактный план

Создать `backlog/implementation-plans/<ID>-<short>.plan.md`, один на задачу.
Шаблон (пути в ссылках — относительно файла, branch с префиксом codex/):

```md
# План: JCR-XXX Название

## Metadata
- source_task: [JCR-XXX](../tasks-ready/JCR-XXX-short.md)
- requirements: REQ-UI-001 (implements)
- branch: codex/JCR-XXX-short
- readiness: no
- dependencies: none

## Цель и границы
Наблюдаемый результат; что не входит в задачу.

## Решения и evidence
Принятые продуктовые и технические решения, дата, владелец и ссылка на источник.
Для технической задачи — конкретная причина отсутствия продуктовой дельты.

## Шаги реализации
Связные этапы, затронутые контракты и вероятные файлы.

## Проверки
Конкретные сценарии, тесты и ручные критерии; что должно обнаружить отсутствие
поведения. Не создавать искусственный failing test, если baseline уже верен
или изменение не требует автоматического теста. Обязательный harness не копировать.

## Открытые вопросы
Блокирующие вопросы; для readiness: yes здесь строго `none`.

## Риски и условия остановки
Только применимые к задаче риски, согласованная реакция и границы решений исполнителя.
```

Несколько REQ в metadata разделять запятой: `REQ-UI-001 (implements), REQ-HIST-001 (constrains)`.
Для технической задачи вместо REQ: `none — конкретная причина`.
Черновик может содержать предложенные REQ или pending, но не разрешает execution.
Readiness yes требует полного согласования, evidence и закрытых вопросов.
Не дублировать в плане общие правила Git, стека и skills.

## Переход

Создание плана оставляет задачу на месте. При запросе начать реализацию
перевести только готовую задачу в implementation, обновить статус, source_task
плана, ссылки, индекс и lifecycle (дата начала, план, ветка). Risky переводить
только после требуемого review. Добавить запись в backlog/logs/implementation-log.md.
Запустить `make requirements-check` и harness. В результате перечислить
планы, готовность и причины пропуска; реализацию выполнять отдельным шагом
через implement-release-plan, если она запрошена.
