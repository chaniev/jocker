# Implement release plan

## Результат и режим

По умолчанию работать в режиме `implementation`:

1. реализовать переданный план или набор планов в task-workspace;
2. проверить итоговый candidate SHA;
3. локально интегрировать изменения в указанную основную ветку;
4. актуализировать связанные планы и документацию;
5. очистить созданные task-ресурсы.

Включать режим `ci` только когда пользователь явно запросил прогон CI
(push ветки). В этом проекте нет внешнего стенда деплоя: release-результатом
считается слитая в `main` ветка с зелёным локальным прогоном; публикация
сборки выполняется только по отдельному явному запросу.

Считать явный вызов skill разрешением на task-ветки/worktree, локальные
коммиты, локальный merge, обновление планов и безопасную очистку созданных
ресурсов. Не считать его разрешением на push, PR или публикацию release.

## Вход и приоритет источников

Принимать путь к одному plan, список путей или manifest. Для списка проверить
все файлы, удалить точные дубликаты путей и сохранить порядок пользователя.
Если путь нельзя однозначно определить, запросить его.

Применять источники в порядке:

1. запрос пользователя;
2. корневой `AGENTS.md` (вложенные `AGENTS.md` подчинены ему);
3. тексты правил в `правила игры/`;
4. код, типы, тесты и конфигурация;
5. build-конфигурация (`project.pbxproj`, схемы);
6. implementation plan как описание требуемого результата;
7. документация в `docs/`.

Полностью читать корневой `AGENTS.md` и релевантные проектные skills
(`.agents/skills/`). Не дублировать эти правила внутри release workflow.

## Короткий preflight

Для одного плана зафиксировать только:

- source-постановку и declared branch (если заданы);
- затронутые области (rules core / Game/ / ViewControllers/ / Models/Bot/ /
  training CLI / build+CI);
- наличие изменений поведения игрока;
- readiness/blocker.

Остановиться до изменения project code, если план противоречит тексту правил
в `правила игры/` или корневому `AGENTS.md`, либо требует непринятого
продуктового решения. Расхождение с правилами — продуктный вопрос, а не
повод молча выбрать сторону.

Не строить dependency graph для одного плана. Для набора планов составить
компактную таблицу: план → ветка → зависимости → затронутые области →
проверки.

Перед изменением project code использовать project `task-worktree` skill. Он
единолично определяет команды создания, проверки, возобновления и очистки
worktree. Не повторять его Git-инструкции здесь и не менять код в
coordination workspace.

## Реализация

Для каждого плана:

1. сверить ожидаемый результат с текущим кодом и тестами;
2. подтвердить task-specific решения, зависимости и stop conditions;
3. добавить конкретный regression evidence в порядке, требуемом планом и
   проектом (тесты в `JockerTests/<feature>/`, при необходимости — расширение
   regression pack);
4. внести минимально достаточные изменения без unrelated refactoring;
5. обновить всех потребителей изменённого контракта;
6. для изменения поведения обновить нормативный текст плана и, при
   структурных изменениях, `FOLDER_STRUCTURE_SPEC.md` в той же задаче;
7. выполнить проверки корневого `AGENTS.md` на финальном candidate SHA:
   `bash scripts/run_all_tests.sh` плюс пакеты, обязательные для затронутой
   области (`make joker-pack` для правил, `make stage4-phase-pack` /
   `make stage6b-pack` для ботов);
8. проверить diff, статус worktree и отсутствие случайных файлов.

Не создавать формальный red test, если текущий baseline уже корректен и
задача является расследованием. Сначала доказать слой проблемы, затем менять
только его.

## Проверки без повторов

Считать результат проверки привязанным к exact candidate SHA/tree.

- Перед merge выполнить полный обязательный набор проверок изменённых
  областей.
- После merge сравнить tree candidate и итоговой основной ветки.
- Если tree совпадает, конфликтов не было и runtime не изменился, использовать
  уже полученное evidence вместо повторного полного запуска.
- Если tree изменилось из-за новой base, конфликтов или межплановой
  интеграции, повторить затронутые проверки.
- Для batch выполнить один совокупный regression pass после последнего merge;
  не запускать одинаковый полный suite после каждого независимого
  fast-forward.

Не объявлять не запускавшуюся проверку успешной. Команды и результаты хранить
кратко: command/filter, SHA, outcome.

## Интеграция и статусы

Интегрировать в подтверждённом порядке по Git-политике проекта. Функциональные
исправления выполнять в task-worktree, а межплановые — в отдельной
integration-fix ветке только когда ошибка действительно пересекает несколько
планов.

После успешной интеграции:

1. проверить достижимость task commits из основной ветки;
2. отметить выполненные пункты плана; незавершённые — оставить явные остатки
   с причиной;
3. актуализировать только фактически завершённые plan status;
4. по возможности включить статус-обновления планов в task-ветку;
5. вызвать project `task-worktree` skill для безопасной очистки.

## Блокеры

Остановиться только когда безопасное продолжение невозможно: отсутствует plan,
нельзя определить требуемый контракт/зависимость, есть необъяснимые изменения,
нужен продуктовый выбор или миграция накопленных данных (статистика,
история) несёт риск потери без recovery. Сначала продолжить независимые
части, если это не ухудшает состояние.

## Финальный отчёт

Сообщить только применимое:

- выполненные plans, порядок и итоговые SHA;
- изменённые контракты и области;
- проверки с привязкой к SHA;
- актуализированные статусы и очищенные ресурсы;
- оставшиеся блокеры или ручные действия.

Не утверждать выполнение действия без evidence.
