# ADR-0001: Надёжное сохранение и завершение партии

## Status

Accepted (пользователь текущего чата, владелец проекта, 2026-11-16).

учтён в решении ниже. Источник —

Реализовано 18.11.2026 в локальной main (`24350b7`); проверки и ограничения — в [JCR-001](../../../backlog/done/2026-11-18/JCR-001-save-and-resume.md#выполнение-и-проверка--18112026).

См. [продуктовое уточнение](#продуктовое-уточнение--16112026): оно имеет приоритет
над прежними ограничениями ожидания в пунктах 3–4 и Consequences ниже.
Принятый выбор атомарных файлов, receipts и дедупликации сохранён.

## Context

Нужно продолжение после последнего действия для трёх независимых вариантов игры,
сохранность после обновления, сообщение об ошибке записи и однократная фиксация
итога даже при закрытии до просмотра результатов.

- `GameStatisticsStore.recordCompletedGame` не получает идентификатор партии;
  `UserDefaultsGameStatisticsStore` увеличивает агрегаты при каждом вызове.
- `GameResultsPersistenceCoordinator` предотвращает повтор лишь флагом
  `GameSceneSessionState.hasSavedGameStatistics` в памяти. Запись статистики
  вызывается при закрытии итогового окна, а не при завершении партии.
- `DealHistoryExportService` уже пишет JSON-файлы атомарно в Application Support;
  автоматические экспорты блока сейчас не имеют постоянного идентификатора партии.
- `GameState` не содержит рук и текущей взятки; снимок должен объединять состояние
  правил, счёта, истории и продолжения потока, не сериализовать UIKit/SpriteKit.
- Корневой [AGENTS.md](../../../AGENTS.md) задаёт `UserDefaults` для persistence
  и принятое владельцем исключение JCR-001 для файлового хранилища сессий и
  канонической статистики; настройки остаются в `UserDefaults`.

По документации Apple запись `UserDefaults` обновляет память сразу, диск —
асинхронно; `synchronize()` применять не рекомендуется. Поэтому чтение сразу
после `set()` не доказывает сохранность перед уничтожением процесса.
[Apple: UserDefaults](https://developer.apple.com/documentation/foundation/userdefaults),
[Apple: synchronize](https://developer.apple.com/documentation/foundation/userdefaults/synchronize()).

## Decision

Принята следующая стратегия.

1. **Снимок сессии вместо воспроизведения истории ходов.** Стабильный DTO с
   `schemaVersion`, `matchID`, `revision`, вариантом игры, снимками состояния
   правил/счёта/истории и явным курсором следующего действия. Случайные результаты
   уже выполненной раздачи сохраняются; восстановление не запускает shuffle,
   повторный заказ, ход или начисление. Незавершённая анимация не является
   отдельным игровым действием и при загрузке заменяется согласованным состоянием.
2. **Три независимых файла слотов.** В приватном Application Support/Jocker
   хранить по одному контейнеру для `threePlayers`, `fourPlayersFreeForAll`,
   `fourPlayersPairs`. Каждый контейнер заменяется атомарно; методы протокола
   возвращают различимые ошибки чтения, версии, валидации, записи и удаления.
   Никаких обращений к внутренним файлам базы `UserDefaults`.
3. **Последовательные записи и отдельные ревизии игры/сохранения.** Одна serial
   queue с completion handlers, без Swift concurrency. Для каждого игрового
   перехода записывается согласованный снимок со всеми его эффектами. При
   успешной записи checkpoint соответствует последнему действию. По решению
   владельца ошибка автосохранения обычного хода не вызывает сообщения, паузы,
   отката или выхода: live state остаётся актуальным, следующие игроки/боты
   продолжают; persisted revision не продвигается. Следующая штатная запись
   содержит полный актуальный live snapshot со всеми промежуточными действиями,
   не повторяет их выполнение и не строится на старом сохранении. Без отдельного
   диалога или цикла немедленных повторов. До успеха перезапуск возвращает только
   последний успешно записанный checkpoint (если он есть). Снимок снимается на
   main thread, кодирование/диск — вне него. Проверка `matchID`/ревизии отклоняет
   запоздалые callbacks после выхода, удаления или замены партии. Фон/выход
   дожидаются уже принятой записи; при явном выходе сохраняется актуальный live
   snapshot. Завершение процесса не является единственным моментом сохранения.
   После ошибок полный снимок может продвинуть persisted revision с `n` сразу
   на `n+k`; обязательной цепочки записей `n+1` нет. Запоздалый запрос/ответ
   не откатывает ни live state, ни persisted revision, ни содержимое файла.
4. **Завершение как восстанавливаемая транзакция.** В переходе последней раздачи
   записать в слот терминальный receipt с `matchID`, итогами и историей. Он не
   доступен через «Продолжить». Затем применить статистику и финальный экспорт,
   после успеха очистить receipt. При старте приложения повторить незавершённые
   шаги до предложения новой игры этого варианта. Итоговое окно не владеет записью.
   Успешный финал подтверждать только после записи terminal receipt. Если
   ошиблась сама эта запись, receipt на диске ещё нет: не объявлять финал
   успешным, показывать ошибку завершения и повторять фиксацию того же результата,
   не начисляя его заново. Исключение обычного автосохранения на этот шаг не
   распространяется; после уничтожения процесса до commit доступен лишь ранее
   записанный active checkpoint.
5. **Каноническая статистика с дедупликацией.** Отдельный атомарный контейнер
   `{schemaVersion, snapshot, appliedMatchIDs, legacyImportVersion}`. Изменение
   агрегата и добавление `matchID` происходят одной записью. Повтор receipt — no-op.
   Все три слота, recovery и экраны используют один app-owned repository и
   общий сериализованный read-modify-write, а не отдельные writers из каждой
   фабрики/сцены. Метаданные ID не являются архивом сыгранных партий. Существующий протокол
   расширить идентификатором и результатом операции; consumer-экраны получают
   прежние агрегаты. После переключения не должно остаться второго writer в UD.
6. **Миграция без обнуления.** При отсутствии нового контейнера импортировать
   существующий v2 или v1 из UD, сохранив текущую нормализацию и все scopes.
   Маркер импорта и данные фиксируются одной атомарной записью. Старые ключи
   оставить нетронутыми для диагностики; не использовать как второй актуальный
   источник. Ошибка чтения/импорта не трактуется как пустая статистика. При
   наличии повреждённого нового контейнера не откатываться молча к старому UD.
7. **История принадлежит партии.** Автоматические экспорты незавершённых блоков
   хранить как внутренние материалы сессии по `matchID`, не публиковать как
   завершённую игру. Материалы размещать в стабильном namespace выбранного
   слота с manifest: очистка не требует декодировать повреждённый active snapshot.
   Замена — восстанавливаемый discard: атомарный tombstone/receipt с владельцем
   материалов запрещает продолжение, затем удаляются материалы и завершается
   очистка слота. При перезапуске cleanup продолжается; новая партия запускается
   после его успеха. Запоздалая запись старого matchID отклоняется.
   Финальный экспорт имеет детерминированный путь по `matchID`, повтор не создаёт
   дубль. Старые файлы без владельца не удалять по догадке. Копии, вручную переданные
   пользователем вне приложения, не являются управляемым сохранением.
8. **Обновления.** Версия формата независима от версии приложения. Для каждого
   выпущенного формата сохранять decoder/миграцию и эталонный fixture; сначала
   преобразование и проверка в памяти, затем атомарная замена. Не менять смысл
   сыгранных результатов и не сбрасывать сохранения при обычном обновлении.

Атомарная запись через временный файл уменьшает риск частично записанного
контейнера; сама по себе она не делает несколько файлов одной транзакцией.
Именно receipt + дедупликация обеспечивают восстановление между шагами.
Не обещается защита от аппаратной потери накопителя или мгновенного отключения
питания на уровне fsync; проверяемый контракт — перезапуск/уничтожение процесса.
[Apple: atomic](https://developer.apple.com/documentation/foundation/nsdata/writingoptions/atomic).

## Options compared

| Вариант | Достоинства | Почему выбран/отклонён |
|---|---|---|
| Один сериализованный объект в UD со слотами и статистикой | Следует текущему стеку, мало адаптеров | Нет подтверждаемого результата дисковой записи каждого действия; не закрывает требуемую обработку потери прогресса и процессный crash-контракт |
| Файлы слотов + атомарная статистика + receipt | Явные ошибки, независимые слоты, однократный итог, Foundation уже используется для экспорта | Выбрано владельцем; миграция агрегатов и исключение из правила UD приняты |
| Журнал событий с восстановлением через replay | Компактные записи действий | Тесно связан с версиями правил, случайностью, ИИ и side effects; сложнее обеспечить совместимость обновлений; для текущего объёма избыточен |

## Consequences

Дополнительные DTO, валидация, миграции и тесты прерываний обязательны.
Каждое действие требует попытки записи; нужны замеры задержки на полном сохранении
с историей. Нельзя ускорять за счёт пропуска подтверждённых действий или
дебаунса, допускающего потерю прогресса. Память/объём списка `appliedMatchIDs`
растут с числом игр; не вводить удаление ID без доказанной безопасной политики.

При ошибке сохранения во время выбранного выхода используется согласованный
сценарий сообщения о потере прогресса и выхода. Для ошибки автосохранения
обычного хода владелец выбрал отсутствие реакции интерфейса: игра продолжается,
а до следующей успешной записи несохранённый прогресс может быть утрачен при
перезапуске. Эта оговорка не разрешает намеренно пропускать штатные сохранения
и не меняет обработку ошибок финализации, удаления и явно выбранного выхода.
Ошибка последующих шагов финализации после commit receipt оставляет невидимый
для продолжения receipt на повтор; новая партия того же слота не должна затереть
его. До первого commit нельзя утверждать, что receipt существует и обеспечивает
восстановление итогов.
Тексты и кнопки ошибочных состояний определены в плане.

## Affected layers and consumers

`Models/Gameplay`, `Scoring`, `Game/Scenes`, `Game/Coordinator`,
`Game/Services/History`, `Game/Services/Statistics`, стартовый поток UIKit,
`AppDelegate` и соответствующие тесты. Новые persistence-типы не принадлежат
training CLI; общие модели сохраняют совместимость его сборки. Настройки,
правила подсчёта, сложности и алгоритмы ботов не меняются.

## Validation

- Новый экземпляр хранилища/процесса восстанавливает последнее успешно записанное
  состояние; без ошибок записи это последнее выполненное действие. Убийство
  процесса в границах prepare/write/replace/ack не создаёт
  половинного состояния или повторного хода.
- Ошибка обычного автосохранения не блокирует игру, не показывает сообщения и
  не отменяет ход. Серия ошибок и следующая успешная запись сохраняют актуальное
  состояние со всеми промежуточными действиями; kill до успеха восстанавливает
  прежний checkpoint. Явный выход повторно сохраняет live state и сообщает о
  потере прогресса только при ошибке этой операции.
- Kill между receipt, статистикой, экспортом и очисткой даёт ровно один итог;
  терминальная партия никогда не предлагается продолжить.
- Ошибки записи/удаления и запоздалый callback не воскрешают заменённую партию.
- Kill между discard tombstone, удалением материалов и очисткой слота доводит
  удаление до конца; повреждённый снимок не мешает очистке своего staging namespace.
- Несколько терминальных слотов, восстанавливаемых при одном запуске, не теряют
  обновления общих агрегатов или appliedMatchIDs.
- Импорт v1/v2 сохраняет агрегаты, повторный запуск не импортирует заново;
  повреждённые данные не превращаются молча в нулевую статистику.
- Миграции каждого выпущенного формата и установка обновления поверх сборки
  с тремя сохранениями сохраняют доступное продолжение.
- Reviewer по игровым правилам проверяет снимки начислений; reviewer клиента —
  курсоры/модальные окна/callbacks; исключение UD принято владельцем проекта.

## Продуктовое уточнение — 16.11.2026

Источник: три ответа владельца в текущем чате, дословно сохранённые в
[JCR-001](../../../backlog/done/2026-11-18/JCR-001-save-and-resume.md#дополнительные-решения-по-плану).
Это уточнение наблюдаемого поведения; новый способ хранения не выбирался.

- Ошибка самого первого сохранения обрабатывается так же, как ошибка обычного
  автосохранения: без сообщения, игра продолжается. Пока успешного checkpoint
  нет, восстановление после перезапуска недоступно; следующая штатная запись
  сохраняет полный актуальный снимок.
- При ошибке записи terminal receipt доступен выход в меню после сообщения
  о потере несохранённого результата. Повтор записи не является обязательным
  условием выхода. До commit восстановление итога не обещается; ранее записанный
  active checkpoint остаётся доступен, если существует. Уже записанный receipt
  при выходе сохраняется для однократного применения.
- Ошибка чтения/импорта накопленной статистики не блокирует продолжение или
  новые партии, включая тот же вариант. В этом случае прежнее требование
  дождаться полной финализации перед новой игрой не применяется. Запрет
  затирать receipt остаётся: ожидающие учёта итоги должны переживать новые
  партии, их замену и перезапуск, не превращаясь в дополнительные предложения
  «Продолжить». Их учёт и cleanup не затрагивают новую active-партию. Недоступная
  статистика не подменяется пустой; данные сохраняются до восстановления доступа.

Проверки дополнения: сбой первого checkpoint; выход при постоянном сбое terminal
commit; недоступная статистика и несколько следующих партий одного варианта;
перезапуск, discard новой партии и последующее однократное применение всех
сохранённых результатов. Конкретные этапы и критерии отражены в плане JCR-001.
