# Реестр требований Jocker

Реестр описывает желаемое поведение приложения, а не историю разработки.
Принятые карточки — продуктовый контракт; предложенные карточки не разрешают реализацию.
Процесс адаптирован из Gym CRM 15.11.2026, без переноса требований CRM.

## Источники и границы

Явное решение пользователя фиксируется в карточке с датой и источником.
Для игровых механик первоисточник — [тексты правил](../../правила%20игры/).
Реестр дополняет их требованиями к продукту, но не переопределяет раздачу,
заказы, козырь, джокера, подсчёт очков и пары. Конфликт требует явного
продуктового решения до реализации. Правила не архивируются этим переносом.
Код и тесты показывают фактическое поведение, а не согласие на новое.
UX-контракты, ADR и планы должны соответствовать принятым требованиям.

Первичное наполнение ограничено существующим продуктовым бэклогом:
13 предложений, без аудита реализации. Исследования PROD-014/015 пока `pending`.
Исторические планы в `docs/` не объявляются принятыми или завершёнными:
при возобновлении связать их с актуальной задачей и новым планом в backlog.
Полная инвентаризация всех игровых требований не выполнялась.

## Два независимых статуса

- **Решение:** `предложено` → `принято` либо `отклонено`.
- **Реализация:** `не начато` → `частично` → `реализовано`.

`принято` требует явного решения пользователя/владельца продукта; оно уже может
содержаться в запросе — не спрашивать повторно. `реализовано` означает
подтверждение текущей редакции в main, а не только наличие task-ветки.
Каждое изменение текста или статуса сопровождается датированной записью
с рабочей ссылкой на задачу/план и строкой в [CHANGELOG](CHANGELOG.md).
Для новой принятой редакции ранее реализованного требования реализация
сбрасывается в `частично` или `не начато` до интеграции.

## Связь с задачей

Каждая активная карточка содержит:

```md
## Requirements
- REQ-UI-001 — implements
```

Отношения: `implements` — реализовать уже принятую редакцию; `changes` — изменить
нормативное поведение; `constrains` — соблюдать ограничение; `verifies` — проверить
уже требуемое поведение. Для `changes` принять и записать целевой текст до реализации.
Несколько связей записываются отдельными строками.

Техническая работа без изменения поведения: `- none — конкретная причина`.
Неопределённое решение: `- pending — что нужно решить`, только в
`needs-clarification`. Эти варианты нельзя смешивать с REQ-связями.
В `tasks-ready`, `risky`, `implementation` все REQ должны быть приняты.
Исследовательская задача может использовать обоснованный `none`, когда её
результат согласован и она не меняет поведение приложения.

План содержит `- requirements: REQ-UI-001 (implements)` с теми же связями,
либо `none — причина`. Неготовый план имеет `readiness: no`; он не разрешает
реализацию. Перед готовностью закрыть продуктовые и существенные технические
решения. Требования, историю и CHANGELOG обновлять в той же задаче, которая
меняет поведение. После интеграции отметить только подтверждённую реализацию.

## Проверки

`make requirements-check` проверяет карточки, ссылки, статусы и планы.
`make requirements-check BASE=origin/main` дополнительно требует изменение
CHANGELOG вместе с доменными файлами (включая новые неотслеживаемые файлы).
Эта проверка входит в `make harness-verify` и `make harness-ci`.
Она не доказывает согласование человеком или полноту реализации: это проверяют
по источникам решений, коду, тестам и интеграции.
