# Продуктовый бэклог Jocker

Создан 15 ноября 2026 года по предложениям из продуктового разбора в текущем чате проекта и запросу владельца занести каждое предложение в бэклог. Все 15 задач зарегистрированы со статусом **needs-clarification**; реализация не начата. Карточки фиксируют предлагаемый результат и критерии приёмки. Приоритеты и объём предварительные; открытые продуктовые решения не считаются согласованными.

Базовая гипотеза: знакомому с джокером игроку нужна удобная игра против ботов с безопасным продолжением и возможностью улучшать мастерство. Проверка этой гипотезы входит в PROD-014. Текущий код рассматривался на коммите `a52efec`; риски интерфейса и поведения, не воспроизведённые на устройстве, отмечены в соответствующих карточках.

## Соответствие предложениям

- Восемь основных направлений дорожной карты: PROD-001–PROD-008, по одной карточке на направление.
- Повтор партии, возврат из таблицы, обозначение партнёра, темп анимаций и читаемость небольшого экрана: PROD-009–PROD-013.
- Пилот и сбор продуктовых сигналов: PROD-014.
- Проверка монетизации после подтверждения повторного использования: PROD-015.

Возврат из таблицы вынесен из общего улучшения обратной связи в отдельную PROD-010, чтобы не дублировать работу. Проверка сложности ботов и качества партнёра входит в пилот; отдельного задания на усиление AI пока нет. Сокращённая партия остаётся возможным дальнейшим решением в PROD-006, а не утверждённым изменением правил. Публичный онлайн, рейтинги и подписка не включены в реализацию автоматически.

## Порядок работы

1. Воспроизвести и устранить раскрытие карт — PROD-002. Параллельно готовить протокол и набор участников PROD-014.
2. Обеспечить продолжение PROD-001; подготовить понятный старт PROD-003, обратную связь PROD-004, возврат PROD-010 и проверку экранов PROD-013.
3. Провести самостоятельное использование в пилоте после готовности сборки. Раннее наблюдение с исследователем возможно с явно указанными ограничениями.
4. По результатам выбрать разбор PROD-005, тренировки PROD-006 и/или прогресс PROD-007. Небольшие улучшения PROD-009, PROD-011 и PROD-012 планировать по выявленным затруднениям.
5. Рассматривать приватную игру PROD-008 и монетизацию PROD-015 после соответствующих сигналов спроса.

## Как вести карточки

- P0 — риск честности или целостности результата, который нужно проверить и устранить первым; P1 — ближайшая надёжность и понятность; P2 — следующий слой ценности; P3 — развитие после проверки спроса.
- Одна карточка хранит проблему, результат, объём, критерии приёмки, сигнал результата, зависимости и вопросы. Ссылки на связанные задачи не всегда означают жёсткую очерёдность; обязательные предшественники названы явно.
- До implementation plan закрыть блокирующие продуктовые вопросы. После этого зафиксировать ответы и их источник в карточке; не выдавать предлагаемое поведение за принятое.
- При изменении статуса обновлять карточку и эту таблицу. Наличие карточки само по себе не разрешает запуск реализации, пилота, приглашений или платежей.
- Идентификаторы PROD-001–PROD-015 постоянны. Новые задачи получают следующий свободный номер.
- Карточки хранятся в очереди своего статуса. Переходы проверяются валидатором; автоматического согласования или запуска реализации нет.

Контекст: [продуктовый разбор сентября 2026 года](../docs/PRODUCT_OWNER_REVIEW_RU.md). Это более ранний материал: при расхождении с текущим поведением сверять исходники и актуальную карточку. Бэклоги [рефакторинга](../docs/CODE_REFACTORING_BACKLOG.md) и [улучшений ботов](../docs/BOT_AI_IMPROVEMENT_PROPOSALS_UNIFIED.md) сохраняют свою область ответственности.


## Обработка требований

Процесс перенесён из CRM. [Реестр требований](../docs/requirements/README.md)
описывает нормативные карточки, согласование и связь с задачами.
Правила работы агента: [AGENTS.md](AGENTS.md).

| Каталог | Назначение |
|---|---|
| inbox/ | Входящие заметки, ещё не разобраны |
| processing/ | Временная обработка выбранных заметок |
| processed/ | Сохранённые исходные заметки после разбора |
| needs-clarification/ | Не согласован результат или есть блокирующие вопросы |
| tasks-ready/ | Приняты требования, результат и границы ясны |
| risky/ | Приняты требования, но нужен конкретный review риска |
| implementation-plans/ | Планы незавершённых задач; план сам по себе не запускает работу |
| implementation/ | Явно начатая реализация с готовым планом |
| done/YYYY-MM-DD/ | Завершённая задача, её план и постоянные свидетельства |
| logs/ | Дополняемые журналы обработки, планирования и сверки статусов |

Пустые очереди создаются при первом использовании; список выше — полный контракт.
Идентификаторы PROD сохраняются. Новые продуктовые задачи используют следующий
PROD, технические — TASK; номера искать рекурсивно, включая архив.

### Как пользоваться

- `зафиксируй …` (также `зафикчируй`) — дословно добавить текст после первого
  триггера в `inbox/YYYY-MM-DD.md` по дате пользователя. Не запускать разбор.
- `разбери входящие требования` — разобрать заметки, проверить дубликаты,
  связать с REQ, создать/уточнить карточки, сохранить исходники в processed.
- `сверь статусы задач` — сверить выбранные карточки с кодом, проверками и main;
  не обрабатывать входящие автоматически.
- `подготовь планы для готовых задач` — создать планы, указать решения,
  проверки и готовность. Переводить в implementation только по запросу начать работу.
- `реализуй план …` — выполнить согласованный план в отдельной рабочей ветке,
  проверить, интегрировать и обновить требования и статусы.

### Завершение

Для реализации дата done — дата подтверждённой интеграции в main, для закрытия
дубликата/исследования — дата подтверждённого решения или результата.
Записать `completed_at` и `completion_date_evidence`; не подменять старую дату
датой сегодняшнего разбора. При неизвестной дате оставить вопрос открытым.
Перенести карточку и план вместе, исправить относительные ссылки и индекс.
Отчёты сборки остаются в `.derivedData/`; постоянное резюме evidence — в карточке.
Старые журналы не переписывать, добавлять новые записи.
